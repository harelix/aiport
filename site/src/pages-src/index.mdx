## Why it exists

If you build with LLMs, the day probably looks like this: Claude Code in one
repo, Codex in another, a model running in Ollama, and credits with two or
three providers. Every app you write ends up with its own copy of the provider
setup and its own keys, and when a call starts failing you find out from a user.

aiport sits in the middle. Your apps point one OpenAI-style or Anthropic-style
client at it, and it passes each call to the provider you picked. The keys stay
with aiport, and each app gets a token of its own that you can revoke.

## What it does over time

Apps don't have to name a model. They can ask for `fast`, `balanced` or `best`
and leave the choice to you, so moving an app to a cheaper or newer model is a
change in the dashboard, not in its code.

aiport also keeps a record of every call (which app, which model, how long it
took, whether it worked). It never stores prompts or answers. When the same
failure keeps coming back, it opens an Issue with the evidence and two ways to
fix it: a change on aiport's side that you approve, and an instruction you can
paste to the app's coding agent. If your app shows a thumbs up and down next to
its answers, those votes turn into suggestions about which model should handle
what.

You approve changes yourself (unless you turn on automatic fixes), and any of
them can be undone.

## What it doesn't do

It is a single-user tool. There are no teams, budgets or shared dashboards. If
you need those, LiteLLM, Portkey or Bifrost are a better fit. It also never
translates between protocols, so an OpenAI client can only reach providers that
speak the OpenAI protocol. And it is still experimental: no provider and agent
combination has passed the full compatibility check yet.
